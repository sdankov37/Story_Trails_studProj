## Бланк 2. Альтернативы и критерии

**Критичный выбор и почему он важен:** Выбор СУБД (PostgreSQL vs SQLite). Это критично, так как от этого зависит надежность бронирования (Правило П2 — исключение овербукинга) и безопасность данных при конкурентных запросах.

**Вариант А:** PostgreSQL (Клиент-серверная СУБД).
**Вариант Б:** SQLite (Встроенная файловая БД).

**Что у вариантов одинаково и почему:** 
Обе технологии поддерживают реляционную модель, транзакции ACID и могут работать с Node.js (через библиотеки `pg` или `better-sqlite3`/Prisma ORM).

**Какие части системы изменяются, если выбран другой вариант:**
*   **Инфраструктура:** PostgreSQL требует запуска отдельного сервера БД (через Docker). SQLite работает как файл внутри контейнера с API.
*   **Драйвер БД:** Изменятся настройки подключения в Prisma ORM (строка подключения).

| Критерий или обязательное условие | Источник в проекте | Признак соответствия и способ проверки |
| :--- | :--- | :--- |
| **Защита от двойных броней (Конкурентность)** | Правило П2 (ПЗ №7) | БД должна поддерживать блокировки строк (row-level locking) или ограничения исключения (EXCLUDE). |
| **Соблюдение строгих ограничений (Constraints)** | Правила П3, П4, П5 | Поддержка ENUM, CHECK, UNIQUE, FOREIGN KEY. |
| **Сложность эксплуатации и развертывания** | Ограничение по времени (семестр) | Насколько просто развернуть и поддерживать решение. |

## Бланк 3. Сравнение и источники

**Область сравнения:** Хранение данных о бронированиях и слотах.

| Критерий из бланка 2 | Вариант А: PostgreSQL | Вариант Б: SQLite | Вывод для проекта |
| :--- | :--- | :--- | :--- |
| **Защита от двойных броней** | Поддерживает блокировки строк (`SELECT FOR UPDATE`). Поддерживает `EXCLUDE constraint`, который атомарно запрещает пересечение временных интервалов. [К1] | Поддерживает транзакции, но блокирует файл БД целиком при записи. `EXCLUDE constraint` отсутствует. Требует ручной проверки в коде. [К2] | **PostgreSQL выигрывает.** `EXCLUDE constraint` — идеальное решение для правила П2. |
| **Ограничения схемы (Constraints)** | Полноценная поддержка ENUM, CHECK, сложных ограничений. [К3] | Поддерживает базовые CHECK и UNIQUE, но нет настоящих ENUM (только имитация через CHECK). [К2] | PostgreSQL лучше подходит под модель данных ПЗ №7. |
| **Эксплуатация** | Требует отдельного сервиса (Docker). Есть риск отключения сервера. | Один файл. Не требует настройки сети. | SQLite проще для локального старта, но для конкурентного веба PostgreSQL надежнее. |

## Бланк 4. Хранилище и правила данных

**Часть А. Шесть вопросов к хранилищу**

| Вопрос | Ответ для варианта А (PostgreSQL) | Ответ для варианта Б (SQLite) |
| :--- | :--- | :--- |
| Транзакции нескольких записей | Поддерживаются (BEGIN/COMMIT). | Поддерживаются. |
| Изоляция и гарантии | По умолчанию Read Committed. Можно использовать Serializable. | Блокировка на уровне файла. При попытке записи во время другой транзакции — ошибка `SQLITE_BUSY`. |
| Ограничения схемы | Богатый набор: CHECK, UNIQUE, FK, EXCLUDE. | CHECK, UNIQUE, FK (если включен PRAGMA foreign_keys=ON). |
| Копии данных (Реплики) | Возможны (Streaming Replication). | Отсутствуют (один файл). |
| Поведение при потере связи | Разрыв TCP-соединения с сервером БД. Транзакция откатывается. | Файл БД недоступен только если упал диск/процесс. |
| Гарантии отдельных операций | Можно комбинировать уровни изоляции и блокировки. | Жестко ограничены движком SQLite. |

**Часть Б. От модели к хранению (Фрагмент)**
*Выбранное хранилище:* **PostgreSQL 16**

## Бланк 5. Решение и последствия

**Выбрано:** PostgreSQL (в качестве основной СУБД для контейнера «Центральная БД»).
**Статус:** Принято для проектирования.

**Решающие требования и основания:** 
*   Правило П2 (защита от двойных броней). Наличие `EXCLUDE constraint` в PostgreSQL позволяет гарантировать целостность на уровне БД без написания сложных блокировок в коде. [К1]

**Почему другой вариант не предпочтителен:** 
SQLite отлично подходит для прототипов, но его модель блокировки на запись (один writer) может вызвать проблемы при конкурентных запросах на покупку туров в пиковые часы.

**Какое преимущество альтернативы теряем:** 
Простота развертывания (SQLite не требует отдельного Docker-контейнера). Мы принимаем это, так как у нас есть `docker-compose.yml`.

**Риски и неизвестные:**
| Риск | Что проверить | Ответственный |
| :--- | :--- | :--- |
| Задержка сети до БД | Настроить пул соединений (PgBouncer или встроенный в Prisma) | Руслан (Backend) |
| Сбои при проведении транзакций | Написать тесты на откат транзакции (rollback) | Руслан (Backend) |

**Изменения проектных документов:**
*   В **ПЗ №5** (Контейнеры) убираем пометку «предварительно» у PostgreSQL.
*   В **ПЗ №7** уточняем, что ограничение `UNIQUE` для броней реализуется через `EXCLUDE` constraint.
